# 元指令、生成来源与历史改写

本文说明 AP 在每次生成开始时如何**分类**这一轮（元指令、正则标记、内置任务、生成来源），如何**选择工作流**，以及发送前如何**改写聊天历史**（剔除元指令、省 token）。清单字段见 [manifest.md](manifest.md) 的 `meta`、`regex`、`tokenSaving` 部分。

## 元指令

元指令是用户写给叙述者本人的话，以触发词（`meta.trigger`，默认 `@{{ap::name::<narrator>}}`，如 `@Freesia`）开头。

**识别规则**：

- 触发词先做 `{{ap::name::…}}` 与 ST 宏展开，然后**大小写不敏感**地查找；
- 触发词后紧跟字母、数字或下划线时不算（`@Freesiax` 不是触发）；
- **段落写法**：从触发词到下一个空行（`\n\s*\n`）或输入结尾。开头的空白、`,` `，` `:` `：` 去掉；
- **花括号写法**（`meta.wrap: true` 时）：`@Freesia{ … }`，花括号可嵌套，可跨段落；
- 一条输入里可以有多段元指令。

用户可在面板配置页「元指令」区块关闭元指令（配置 `meta.enabled`，默认 `true`）。关闭后输入一律按普通输入处理：不识别触发词（`meta.present` 恒为假、不产生纯元指令或混合轮次、不检查 `meta.tasks`），历史中较早用户消息里的元指令文字原样发送，`{{ap::recent_meta}}` 为空，ST 的代写按钮也不再被拦截、按原生代写执行。已有的纯元指令轮次仍按下文从历史中剔除。

去掉所有元指令片段后：

| 剩余内容 | 分类 | 条件变量 |
| --- | --- | --- |
| 没有元指令 | 普通输入 | `meta.present == false` |
| 空 | **纯元指令** | `meta.present && meta.pure` |
| 非空 | **混合** | `meta.present && meta.mixed` |

元指令文字可用 `{{ap::input::meta}}`（各段以空行连接）读取；`{{ap::recent_meta}}` 输出最近 `meta.recentCount` 次元指令及叙述者的回复（见 [macros.md](macros.md)），条件变量 `meta.recent` 表示它非空。

## 正则标记

`regex` 中的每条规则在分类时求值，结果写入 `flags.<id>`：

- `target: input`（整条输入）、`meta`（元指令片段，以空行连接）或 `recent:<N>`（最近 N 条消息，最多取到最近 6 条）；
- 匹配并且 `requires` 条件成立时为真。`requires` 求值时只能使用 `meta.*` 与 `flags.*`（前面规则的结果）。

## 内置任务

**只在纯元指令时**检查 `meta.tasks`，先 `summary` 后 `impersonate`，第一个成立的条件决定 `meta.task`：

```yaml
regex:
  - { id: summary, pattern: "总结|summar", target: meta }
  - { id: impersonate, pattern: "代写|write my", target: meta }
meta:
  tasks: { summary: flags.summary, impersonate: flags.impersonate }
```

任务本身不改变流程，只是给模组一个条件（例如 `when: 'meta.task == "summary"'` 的模组请求 `recap` 结构）。点击 ST 的代写按钮时，AP 把 `meta.impersonatePrompt` 填入输入框并发送（输入框里已有的草稿换行附在后面），所以代写也是一次纯元指令。

## 生成来源

每次生成有一个**来源** `gen.origin`：

- `story`：拦截器参与（ST 原生 `Generate`）、生成类型为 `normal` `regenerate` `swipe` `continue` 之一，并且**不是**纯元指令；
- `task`：其他所有情况——纯元指令、后台生成（`quiet`）、ST 原生代写（`impersonate`）、脚本 / 其他扩展调用（`script`）。

脚本可以强制下一次生成的来源：

```js
AdvancedPreset.nextGeneration({ origin: 'story' }); // 只影响下一次生成
```

### 工作流选择

- `story`：配置 `connection.workflow` 指定的工作流；找不到时用第一个 `kind: story` 工作流；
- `task`：第一个 `kind: task` 工作流（或 id 为 `task` 的工作流）。

**继续**（`continue`）与 ST 原生**代写**（`impersonate`）是“直通”生成：区域照常组装，但不运行工作流、不接管请求，由 ST 原样发送。

## 轮次类型

生成结束后，sidecar 的 `turn` 记录这一轮的类型：

| `turn` | 条件 |
| --- | --- |
| `story` | 故事轮（含纯元指令但模型仍写了正文的情况） |
| `meta-mixed` | 混合元指令的故事轮 |
| `meta-pure` | 任务轮、没有正文、不是总结 / 代写 |
| `summary` | 任务轮、没有正文、`meta.task == "summary"` |
| `impersonate` | 任务轮、没有正文、`meta.task == "impersonate"` |

后三种是**纯轮次**：消息正文 `mes` 为回复的纯文本（没有回复时，代写 / 总结轮为 `…`）。

## 历史改写

拦截器在 ST 组装提示词之前改写**历史副本**（真实聊天不变）：

1. **剔除纯轮次**：`turn` 为 `meta-pure` / `summary` / `impersonate` 的助手消息，连同触发它的用户消息一起不发送（当前输入除外）；
2. **剥离元指令**：较早用户消息中的元指令片段被去掉；剥离后为空的用户消息不发送；当前输入保持原样；
3. **省 token**（启用时，见下）；
4. **结构回传**：结构声明了 `history` 且请求它的模组已开启、`when` 成立时，最近 N 条助手消息（含已被省 token 替换的）中仍为原文的，按模板在正文之前 / 之后插入自己的结构值（见 [structures.md](structures.md#历史回传)）；
5. **批注回传**：有 `annotations` 结构且请求它的模组已开启时，最近几条仍为原文的助手消息带上自己的行内批注（CriticMarkup）。

开启缓存优化后，第 3–5 步的结果对较早的消息是“粘性”的，见 [缓存优化](#缓存优化粘性渲染)。

## 省 token

配置 `tokenSaving.enabled` 为真时（默认关闭），从末尾开始数助手消息：

- 最近 `keepFullTurns` 条助手消息以及它们前面的用户消息保持完整（用户消息与其后的助手回复算同一轮）；当前输入总是保留；
- 更早的消息中：
  - 已被总结覆盖的（真实索引 ≤ 当前总结的 `coversUpTo`）**不发送**，由模组通过 `{{ap::recap}}` 提供总结；
  - 用户消息按 `userInput` 处理：`keep` 原样发送；`truncate` 超过 `truncateUserAfter` 个字符时截断并加 `…`（0 表示不截断）；`remove` 不发送。扩写类写法中正文（及其事件摘要）已包含用户输入，适合 `remove`；
  - 助手消息如果有事件摘要（`synopsis` 结构），替换为 `tokenSaving.synopsisTemplate` 渲染的一行（占位符 `{{time}}` `{{location}}` `{{event}}` `{{summary}}`）；没有则保持原样。

[故事线](#故事线)分组时，深度按重排后的历史计算；预设有 `synopsis` 结构时，**非当前的支线**（不含主线）中的消息无论深度都按上面的规则处理：有摘要的助手消息换成摘要，用户消息按 `userInput` 处理。非当前时的主线仍按深度。

`keepFullTurns`、`truncateUserAfter`、`userInput` 的默认值来自清单 `tokenSaving`，可被配置覆盖。条件变量 `features.tokenSaving` 表示已开启，`recap.present` 表示有生效的总结。

## 缓存优化（粘性渲染）

省 token、结构回传和批注回传都是**滑动窗口**：每一轮都有某条较早的消息换了渲染方式（原文变成摘要、回传的结构或批注被去掉），提示词前缀在那里改变，服务商的提示词缓存从那里开始失效。

配置 `cache.enabled` 为真时（默认关闭），在缓存可能仍然命中的时候，每条历史消息**沿用上一次请求的渲染方式**——原文 / 摘要 / 截断 / 不发送、带了哪些结构、是否附带批注；只有新消息按当前规则渲染。以下任一情况发生时，所有消息一次性按当前规则渲染（**刷新**）：

| 原因 | 条件 |
| --- | --- |
| `first` | 这个聊天没有上一次请求的记录 |
| `ttl` | 距离上一次**成功**请求超过 `ttlMinutes` 分钟（0 表示不限） |
| `model` | 聊天来源、模型或自定义地址改变 |
| `tools` | 传输方式、工具 / Schema、强制调用、并行工具或示范轮次改变 |
| `prompt` | 历史之前的提示词改变（世界书、插在历史前的关键词模组、系统提示词……） |
| `turns` | 推迟变更的连续请求数超过 `maxDeferredTurns`（0 表示从不推迟） |

细节：

- 沿用的渲染一直保持到**第一处无法避免的差异**——新消息、编辑过的消息、删除的消息、ST 的深度注入等。缓存从那里本来就会失效，所以之后的消息直接使用当前规则，不计入推迟；
- 只有某条消息因此保留了旧渲染（与当前规则不同）时才算“推迟”；连续推迟的请求数超过上限时刷新；历史与上一次请求完全相同的请求（重新生成、滑动生成新版本、重试）不算新的一轮；
- 被总结覆盖的消息、纯轮次、元指令剥离不受影响，总是按当前规则处理；
- 状态按聊天保存在浏览器本地（见 [artifact-and-runtime.md](artifact-and-runtime.md#缓存状态)），在请求**成功**（或中止但已有输出）后写入；失败的请求不改变状态；
- 只有故事轮会写入渲染方式；任务轮（总结、代写、记忆整理……）使用同样的沿用规则，命中时只刷新时间；dry run 不写入；
- 调试页“最近组装”显示本次是沿用还是刷新（及原因）、沿用 / 新渲染 / 推迟的条数；请求列表显示服务商返回的缓存命中 token 数。

实现：拦截器把每条历史消息按两种方式渲染，交给 ST 的是沿用版本并带一个不可见标记（私用区字符，不会触发世界书关键词）；提示词就绪后 AP 依据标记找到这些消息，决定从哪里开始换成当前规则，并去掉标记。脚本路径的回填同样处理。

## 用户输入整形

预设声明了 [`inputShaping`](manifest.md#用户输入整形-inputshaping) 时，AP 对本次输入做整形：

1. **判断**：拦截器改写历史之后，如果历史副本以用户消息结尾（`continue` 没有输入），就给这条消息加一个不可见标记（私用区字符，与缓存优化的标记不同），并记下它送出的文字；
2. **定位**：提示词就绪后，在 `historyStart` 与 `historyEnd` 锚点之间找带标记的消息（缺少锚点时在全部消息中找）。找到、并且标记前的文字以记下的文字结尾时，整形生效——ST 在它之后插入的深度注入、作者注释、`quiet` 提示词都不影响；ST 加的名字前缀被识别并保留（`wrap`）或一并去掉（`extract`）；
3. **组装**：条件变量 `input.shaped` 为真，`{{ap::input::text}}` 在区域中先留一个占位符；
4. **缓存优化**之后：`wrap` 把这条消息中的输入换成展开后的模板；`extract` 把输入从消息中去掉，消息只剩名字前缀或空白时整条删除（图片等附件保留在原消息中）；所有占位符换成输入原文；
5. 所有标记被去掉，不会发给模型。

不整形的情况：预设没有声明；历史以助手消息结尾（`continue`、`/trigger`、其他扩展在助手消息后发起的生成）；脚本路径中脚本在聊天之后又加了用户消息；`dryRun`（ST 的 token 计数）；找不到带标记的消息（被其他扩展改写，警告 `input shaping: …`，原样发送）；`extract` 模式下提示词里没有 `{{ap::input::text}}`（放它的区域没有锚点或被禁用，警告 `input shaping: …`，输入留在历史中，绝不丢失）。

脚本路径的回填同样处理：真实聊天以用户消息结尾、这条消息与历史中的某条对齐、且它之后没有其他用户消息时整形。

预填充传输下整形先于预填充整形：`wrap` 后的文字按 `historyItemTemplate` 带上用户前缀；`extract` 后由放回输入的区域决定它出现的位置。

调试页“最近组装”用一个标签显示本次输入是否整形（`输入已包裹` / `输入已提取` / `输入未整形`）。

## 故事线

预设声明了 [`storylines`](manifest.md#故事线-storylines)、且用户没有在配置中关闭（`storylines.enabled`）时，一个聊天可以有多条故事线。

### 标签

- 用户输入以 `#名称` 结尾（名称不含空白与 `#`、不以 `!` / `?` / `@` 开头、不是 `if?`，最多 64 个字符）时，这条输入属于故事线 `名称`；没有标签属于**主线**。标签在消息中隐藏显示、编辑时可见，发给模型的文字不含标签；
- `#` 之前**不需要空格**（`好的#地下室`），但紧跟在 ASCII 字母、数字或 `_` `#` `&` `/` `=` 之后的 `#` 是普通文字（`C#`、`issue#42`、`page#anchor`、`&#39`），所以英文输入仍需在 `#` 前加空格；
- 省略名称：
  - `#`：**最近的一条其他故事线**（本次输入之前最后一条不属于主线的消息所在的故事线），用于在主线与支线之间快速来回；发送时 AP 把输入中的 `#` 改写为 `#名称`（显示与保存的都是改写后的文字）。之前没有其他故事线时去掉标签，按主线继续，并提示；
  - `#!`：同上，并把这条故事线设为主线（见[切换主线](#切换主线)）；
  - `#?`：一条**新支线**，名称由 AI 在回复中给出（见[命名新故事线](#命名新故事线)）；
  - `#!?`：一条**新主线**，名称同样由 AI 给出；
  - `#if?`：一条**新 if 线**，名称由 AI 给出；这一轮 `storyline.if` 就已为真，模型提前知道它写的是 if 线；
- `#@…`（`#@名称`、`#@`、`#@?`、`#@if?`）：同上，并让这条故事线**对其他故事线不可见**（见[可见性](#可见性)）；
- `!` 与 `@` 不能同时使用，主线不能是 if 线：`#!@名称`、`#@!名称`、`#!if?` 不是标签，按文字保留；
- 名称以 `if` 开头（不区分大小写）的是 **if 线**，可以在故事线面板中按故事线改成普通支线，或把普通支线设为 if 线。if 线只是故事中的含义（另一种可能），给模型的提示词可以据此说明；它是否对其他故事线可见另由[可见性](#可见性)决定；
- 主线可以有名称（聊天元数据）。标签写成主线的名称时也属于主线；
- 助手消息的故事线**按滑动分别保存**（`extra.advanced_preset_storyline`）：AP 收到回复时写入。没有保存的（AP 之外生成的、开场白等）以及 system 消息跟随前一条消息。所以修改用户消息的标签会改变这条用户消息的故事线，但不改变它之后已有的助手消息，直到重新滑动；
- 以 `#?` / `#!?` 结尾的用户消息**跟随它之后的助手消息**：属于那条回复（当前滑动）所在的故事线。回复还没有到达时它是一条未命名的故事线。

### 当前故事线

本次输入的故事线；没有本次输入（`continue`、在助手消息后生成）时为最后一条消息的故事线。

以 `#!` 结尾的输入（`#!名称`、`#!?`、解析后的 `#!`）在**收到回复后**才切换主线，但这一轮已经按切换后的样子组装：当前故事线是（新的）主线，原主线作为一条普通支线排在前面；原主线没有名称时，它的分隔消息与新支线一样用 `?` 代替名称。

### 历史的排列

| 当前 | 历史顺序 |
| --- | --- |
| 主线 | [各条普通支线][主线] |
| 支线 X | [其他普通支线][主线][X] |

- 各条支线按在聊天中第一次出现的顺序排列，组内保持原顺序；
- **不可见的故事线只对自己可见**：其他故事线看不到它的消息（不发送）；它自己能看到所有可见的故事线；
- 可见的故事线只有一条时不分组，历史不变；分组时每组之前插入一条 system 消息：主线为 `storylines.mainSeparator`，其他为 `storylines.separator`（`{{storyline}}` 为名称）；
- ST 的上下文裁剪从最前面开始，所以非当前的支线最先被裁掉；世界书扫描看到的是重排后的历史，最近的消息是当前故事线的；
- 世界书的深度注入、作者注释等插在历史中的消息按**相对主线**的位置放置：ST 放在“倒数第 d 条”之前的，在 [其他支线][主线] 中仍放在倒数第 d 条之前（深度 0 在主线末尾、当前支线的分隔消息之前）。开头的新对话提示、末尾的空消息替代文字与群聊提示保持原位，工具调用消息跟随它所属的消息。

### 可见性

（I-161）每条故事线有一个可见性开关，与 if 线分开：

- 默认：if 线不可见，普通支线可见；**主线总是可见**；
- 故事线面板中可以按故事线切换（“对其他故事线可见”），因此可以有可见的 if 线、不可见的普通支线；聊天元数据 `advanced_preset.storylines.hidden`（`{名称: true/false}`），没有记录时按是否为 if 线；
- 输入以 `#@…` 结尾时，**收到回复后**把这条故事线设为不可见（生成失败时不改；`#@名称` 对主线无效）；`#@?` / `#@if?` 的新故事线在命名时设为不可见；
- 可见性**对 AI 透明**：只决定其他故事线的历史中是否出现这条线，没有对应的条件变量或宏，当前故事线的提示词不受影响；
- 一条不可见的故事线被设为主线时，它变为可见；原主线切换后作为可见的普通支线保留。

### 条件变量与宏

`storyline.name` / `storyline.main` / `storyline.if` / `storyline.new`（当前故事线还没有消息，这一轮开始它）/ `storyline.grouped`（历史按故事线分组，即可见的故事线不止一条，在主线上也可能为真）/ `storyline.naming`（AI 本轮为当前故事线命名，此时 `storyline.name` 为空）/ `storyline.namingMain`（AI 本轮为没有名称的原主线命名）/ `storyline.switching`（本轮把当前故事线设为主线，`storyline.main` 同时为真）与 `{{ap::storyline}}`、`{{ap::storyline::main}}`。

### 命名新故事线

预设声明一个 [`storyline` 种类的结构](structures.md#故事线命名-storyline)并由某个模组请求时，AP 在需要命名的轮次请求它，其他轮次不请求（模组照常生效也不发送）：

| 输入 | 请求的子字段 | 收到回复后 |
| --- | --- | --- |
| `#?` | `name` | 回复与这条输入属于新支线 `name` |
| `#!?` | `name`，原主线无名且有消息时加 `previous_main` | 新主线 `name`；原主线以 `previous_main`（或原有名称）保留为支线 |
| `#!名称`、`#!` | 原主线无名且有消息时 `previous_main` | `名称` 成为主线，原主线以 `previous_main` 保留为支线 |
| `#!?` 的滑动 / 重新生成 | `name` | 重新命名新主线；原主线的名称**不再**重新生成 |

- 结构化输出 / 工具传输中，结构的 Schema 只含本轮请求的子字段；文本传输中由预设的提示词说明要写哪些（条件变量 `storyline.naming` / `storyline.namingMain`）；
- 名称会被整理：去掉首尾引号与开头的 `#` `!` `?`，空白换成 `_`，去掉 `#`，最多 64 个字符；与已有故事线（含主线与面板中设置过 if 开关的名称）重复时加 `-2`、`-3`……；没有给出或整理后为空时用通用名称（“支线” / “原主线”，界面语言）；
- `#?` 的新支线名称以 `if` 开头时仍是普通支线（AP 记下 if 开关为关）：这一轮模型看到的就是普通支线；
- `#?` 的输入跟随回复，所以滑动到另一条回复时，输入也属于那条回复的故事线；重新生成会得到新的名称；
- 预设没有请求 `storyline` 结构时，这些轮次都用通用名称（`ap check` 对声明了故事线、却没有模组请求该结构的预设告警）。

### 按故事线读取聊天

AP 从聊天中读取的数据都按**当前故事线看到的顺序**（与历史的排列相同、去掉不可见的故事线）：

- `{{ap::structure::<id>::last}}` 与 `last.<id>`：当前故事线最近一次的值（如回到主线时是主线上一次的状态栏，而不是刚才支线的）；当前故事线还没有值时，取排在它前面的主线的值；
- 结构的历史回传、`{{ap::recent_meta}}`；
- 聊天记忆与剧情总结：按这个顺序折叠记忆事件、取最后一次总结，所以不可见的故事线（默认即 if 线）中写下的记忆和总结只在这条线上有效，可见的支线中的记忆对所有故事线有效。写作页的记忆面板按最后一条消息的故事线显示。

### 省 token 与缓存优化

- 省 token 见[上文](#省-token)：非当前的支线有摘要时总用摘要；
- 缓存优化按故事线**分别保存状态**：在主线与支线之间来回切换时，各自沿用自己上一次的渲染。

### 支线轮次的变量

变量系统（MVU、酒馆助手的聊天变量与消息变量）按楼层顺序保存状态，支线中的更新会被带回主线。配置项 `storylines.freezeVariables`（默认开启）让主线以外的故事线上的轮次**不更新变量**：

- **MVU**：通过它公开的事件（在 SillyTavern 的事件源上）。MVU 解析出某条消息的更新命令时（`mag_command_parsed`），如果这条消息属于主线以外的故事线，命令被清空；更新结束时（`mag_variable_update_ended`）把状态恢复为更新前的状态（其他监听器的修改也撤销）。MVU 于是保存一份未改变的状态。额外模型解析、重新处理旧楼层同样适用（额外模型的请求仍会发出）。消息按正文匹配，正在生成的这一轮的消息按本轮的故事线算（`#!` 的回复在写入故事线之前就算主线，`#?` 的回复算支线）；匹配不到的文本只在支线轮次生成期间冻结；
- **其他脚本写入的酒馆助手变量**：支线轮次开始时记下聊天变量（`chat_metadata.variables`）；消息到达、渲染后与生成结束时，恢复聊天变量，并把本轮中支线消息的消息变量（`variables[滑动]`）设为它之前一条有变量的消息的值（即本轮开始时的状态；只有 `display_data` / `delta_data` 不同的视为未改变）。下一次生成开始或切换聊天后不再处理；
- 不调用 MVU 或酒馆助手的代码，只使用 SillyTavern 的事件源与聊天数据；角色、预设、全局与脚本变量不处理。

预设可以在支线上告诉模型不必输出变量更新（花瓣在 `input` 区域这样做）。

### 切换主线

- 输入以 `#!名称` / `#!?` / `#!` 结尾时，AP **收到回复后**把这条故事线设为主线（生成失败或停止时不切换，输入保持原样，可以重新生成）；`#!?` 的输入记下已切换（`extra.advanced_preset_storyline_switched`），之后的滑动只重新命名新主线；
- 原主线没有名称、又已经有消息时，由 AI 在同一轮回复中命名（见[命名新故事线](#命名新故事线)）；
- 也可以在故事线面板中点“设为主线”：立即切换，原主线没有名称时弹窗询问，取消则不切换；
- 切换时 AP 遍历聊天：原主线的用户消息加上 `#原主线名称` 标签，助手消息（每个滑动）记为原主线；聊天元数据中的主线改为新名称。原主线名称以 `if` 开头时仍作为普通支线；
- 新主线原有的消息（`#新名称`）随之成为主线。

### 面板

- 不在主线上的消息顶部显示一个小卡片：故事线名称，if 线与不可见的故事线另有标记；点击打开故事线面板；
- 故事线面板列出所有故事线及其楼层（有事件摘要时显示事件，否则显示消息开头），点击楼层跳转到该消息；可以切换 if 线、切换可见性、设为主线、给主线命名；
- 配置页提供故事线开关与“支线轮次不更新变量”开关；
- 用户选项卡片、代写结果卡片填入输入框的文字，以及代写按钮发出的元指令：所在消息（代写按钮为最后一条消息）属于主线以外的故事线、且文字本身没有标签时，自动在末尾加上 ` #名称`，因此选项与代写的回复留在同一条支线上（自定义结构组件的 `fillInput` 同样处理）。

### 限制

- `dryRun`（ST 的 token 计数）不经过拦截器，看到的是原顺序、带标签的历史；
- 同时可见的故事线超过 256 条时，第 256 条之后的与第 256 条并为一组；
- 调试页“最近组装”用一个标签显示本次的故事线（悬停显示各组顺序与去掉的不可见故事线消息数）。

脚本路径的回填同样处理：按最后一条消息的故事线排列对齐到的历史消息。

## 脚本路径的回填

脚本 / 其他扩展直接调用生成时拦截器不会运行。AP 在提示词就绪后尝试**回填**：取 `historyStart` 与 `historyEnd` 锚点之间的用户 / 助手消息，与真实聊天从末尾对齐（忽略宏与空白；相等、包含或 Dice 系数 ≥ 0.9 视为匹配，允许跳过少量插入的消息），然后对匹配到的消息执行同样的历史改写。

匹配率低于 90% 或缺少语义锚点时，历史保持原样，并在调试信息中给出警告（`backfill: …`）。回填也会标记本次输入，见[用户输入整形](#用户输入整形)。脚本发起的任务生成不请求结构（见 [structures.md](structures.md#何时请求结构)）。
