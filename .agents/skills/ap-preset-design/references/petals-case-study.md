# 13. 案例：花瓣预设是怎样设计出来的

> 本文件由 `docs/guide/13-petals-case-study.md` 生成（`pnpm sync-skills`），请勿直接修改。

前面各章分别介绍了 AP 的各个概念。这一章换个角度：把[花瓣预设](https://github.com/mirrorange/petals-preset) v7 当成一个完整的作品，看它从“想法”到“文件”的每一步是怎么决定的。你设计自己的预设时，可以按同样的顺序思考。

## 第一步：定下核心体验

花瓣想要的体验是：**一位深爱着用户的文学妖精，和她的小精灵编辑一起，为用户写故事。**

由此确定了几件事：

- **两个角色**：Freesia（叙述者，写故事、回应用户）和 Petals（编辑，提建议、挑毛病）。两个角色制造了“作者 / 编辑”的视角差，让自我批评变得自然；
- **人设贯穿始终**：身份说明、示范对话、工作流里的台词都以 Freesia 的口吻写成；用户用 `@Freesia` 和她说话时，她以自己的性格回复；
- **故事优先**：讨论过程（思维链）显示在消息上方，正文干干净净地留在聊天记录里。

> 你的预设也应该先回答：模型扮演谁？和用户是什么关系？每轮回复包含什么？

## 第二步：划分区域

| 区域 | 内容 | 为什么放在这里 |
| --- | --- | --- |
| `top` | 身份与核心规则 | 开头最重要，决定模型“是谁” |
| `role` | 角色设定与人设对话 | 紧接身份，补充细节 |
| `mode` | 成人内容前言、续写 / 扩写、“我总结了一些写作技巧” | 用对话自然过渡到写作指南 |
| `guidelines` | 语言、长度、各条写作指南、事件摘要与选项格式 | 包在 `<guidelines>` 中，便于在工作流里引用 |
| `writing_style` | 所选文风 | 包在 `<writing_style>` 中，Kardia 的问题会引用它 |
| `settings`（原生） | 角色卡、世界书、人设 | 由 ST 填入 |
| `history` | 剧情总结、最近的元指令对话 | 紧挨聊天记录之前，作为背景 |
| `memory` | 聊天记忆、全局记忆 | 紧挨聊天记录之后，越近越不容易被忘记 |
| `questions` | 本轮的问题清单 | 紧挨工作流，提问阶段马上要用 |
| `task` | 工作流说明或元指令任务 | 靠近末尾，指令更新鲜 |
| `bottom` | “现在开始工作流” | 最后一句话，直接引出输出 |

注意它对“引用”的利用：写作指南、文风都包在标签里，工作流和问题就可以说“请参考 `<guidelines>`”“按 `<writing_style>` 中的步骤分析”。

## 第三步：列出模组

花瓣的 34 个模组按文件夹分类：

| 文件夹 | 模组 | 类型 |
| --- | --- | --- |
| `core/` | `core`（身份、首尾提示、语言与长度规则）、`context`（总结、近期元指令、记忆）、`questions`（问题清单） | 始终生效 |
| `role/` | `role-freesia` | 单选（目前只有一个角色，留出扩展空间） |
| `mode/` | `mode-continuation` 续写 / `mode-expansion` 扩写 | 单选，必须选一个 |
| | `mode-preface` 成人内容前言 | 开关 |
| `guidelines/` | 防回避、禁词表、角色增强、防总结 / 升华、节奏控制…… | 开关 |
| | `narrative-boundaries` 防抢话 / `narrative-proactivity` 允许抢话 | 单选，可都不选 |
| `styles/` | Kardia、Aisthesis、Antheia、Kryos、Melos | 单选“主文风”，可都不选 |
| | Eros（NSFW） | 开关，可叠加 |
| `features/` | 事件摘要、选项、始终请求元回复、跳过思考（Gemini）、反过滤（Gemini） | 开关 |
| `tasks/` | 纯元指令、混合元指令、记忆、总结、代写 | 始终生效，靠条件出现 |

几个值得借鉴的决定：

- **核心功能不做开关**：身份、上下文、元指令处理是预设成立的前提，用户关掉只会出问题；
- **互斥的做单选，可叠加的做开关**：续写和扩写互斥；防抢话和允许抢话互斥；但 Eros 可以和任何主文风叠加；
- **任务类模组“始终生效 + 条件”**：比如 `summary` 写着 `when: meta.task == "summary"`，平时完全不出现；
- **模型专用的功能写清楚**：“跳过思考 (Gemini)”“反过滤 (Gemini)”在名字里就标明适用的模型，默认关闭，由 Gemini 推荐配置打开。

## 第四步：参数

花瓣的参数都在“写作”页：

- **回复语言**（未设置时沿用故事已有的语言）；
- **对话语言**（角色说话用的语言；与回复语言不同时，每句台词后附翻译；未设置时同回复语言）；
- **工作流语言**（Freesia 与 Petals 讨论用的语言，用英文可以节省 Token；未设置时同回复语言）；
- **草稿语言**（仅迭代工作流：用另一种语言打草稿，再用回复语言修改）；
- **回复长度**与**长度策略**（大约 / 至少 / 至多）。

每个参数都配合条件：用户不设置，相关规则就不出现。

## 第五步：工作流

- **Linear**：提问 → 建议 → 写作。提问阶段依赖一份由模组共同提供的[问题清单](https://github.com/mirrorange/advanced-preset/blob/main/docs/guide/10-build-variables.md)；
- **Iterative**：在 Linear 基础上加入草稿和 Petals 的反馈，再修改定稿；
- **Edit**：写完后自检，并以精确替换的方式修改正文；
- **Task**：处理元指令、代写、总结。

每个阶段都写了两份说明：对话式下是 Freesia 和 Petals 的台词（“我会先向 Petals 提出一系列问题……”），指令式下是简明的步骤（“Ask Petals every item under `Mandatory questions` …”）。每个阶段的字段名和工具名也都起了有意义的名字：`ask_questions`、`give_creative_input`、`write_story`、`review_story`、`edit_story`。

## 第六步：适配五种传输方式

对话式（预填充、纯文本）是花瓣的传统强项：

- 整份提示词像一段剧本，大量使用 `{{ap::prefix::user}}`、`{{ap::prefix::narrator}}` 写出用户与 Freesia 的对话；
- 纯文本模式下，要求模型以 Assistant 身份只输出 `<!-- Workflow Start -->`，然后立刻以 `Freesia: ` 开始工作流；结尾的 `<!-- Workflow Indicator -->` 标记了回复从哪里开始；
- 预填充模式下，结尾直接替 Freesia 说出“Let me begin the workflow.”，模型从这里接着写；
- 写作阶段要求先输出 `<START_OF_CONTENT>`，AP 据此找到正文的开头。

指令式（结构化、工具、多工具）则精简了身份说明，强调“每个阶段都交到任务说明指定的字段或工具里”。

## 第七步：内置功能

| 功能 | 花瓣的做法 |
| --- | --- |
| 元指令 | `@Freesia`；纯元指令时 Freesia 思考后用 `<Freesia_Reply>` 回复，只能使用 `<p>`、`<p special>`、`<blockquote>` |
| 记忆 | `<Freesia_Memory>`，只在用户明确要求时更新，标题稳定，替换时写完整内容 |
| 总结 | 关键词“总结 / summary……”触发，`<Freesia_Summary>` 写出完整的新总结 |
| 代写 | 代写按钮或关键词“代写 / 帮我写……”触发，`<Freesia_Impersonate>` |
| 事件摘要 | 每段之后的 `<synopsis>`，默认打开，同时为节省 Token 提供数据 |
| 选项 | 每轮 4 个方向不同的选项，默认打开 |

## 第八步：推荐配置

花瓣为常见模型准备了 8 套配置。比较特别的是 Gemini 配置：使用工具传输、并行工具调用、思维签名，并配合“跳过思考”模组和专门的示范轮次 `init-skip-thought`，让 Gemini 跳过冗长的内部思考，直接进入工作流。

## 第九步：给用户留出扩展空间

- **6 个插入点**：身份之后、角色之后、写作指南内、文风内、聊天记录之后、任务之前；
- **问题清单是构建变量**：用户可以在“我的模组”里加入自己的问题，或删除不需要的内置问题；
- **中文界面**：所有模组、分组、参数、工作流、配置都有中文翻译，提示词本身保持英文。

## 可以直接借鉴的清单

- [ ] 先定角色与核心体验，再写提示词
- [ ] 按“位置”划分区域：身份在头、提醒在尾、记忆紧跟聊天记录
- [ ] 同类内容包进一个标签，方便在别处引用
- [ ] 一个模组讲一件事；核心不做开关，互斥做单选
- [ ] 参数没填就不出现
- [ ] 工作流分轻重几档，每个阶段只做一件事
- [ ] 对话式与指令式各写一份关键说明
- [ ] 元指令、代写时关掉故事专用的内容
- [ ] 为每类主要模型准备推荐配置，并实际测试
- [ ] 开放少量插入点，id 保持稳定
